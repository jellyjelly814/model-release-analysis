# 独立模型子文档模板

参考页：飞书 Wiki 节点 `LGYWwWzemiKinlkJKJhc221tnEd`，标题 `【2026/04/23】GPT-5.5 & 5.5Pro 对抗Opus4.7`。该 token 仅用于说明模板来源，禁止当作当前任务的写入或校验目标；实际目标必须来自用户输入和当前 API 只读回读。

这份参考页及用户确认的四张页面截图是**唯一的子文档模板**，同时约束内容架构、分析密度、图片职责和排版。其他已经存在的模型子文档只能作为待审计对象，不能作为模板或“邻居写法”反向影响新文档。新子文档应继承四列开场证据图、基本信息后的两列证据、Benchmark 左文右图、三列发布 / 社区语义区块和高分辨率原图；这些规则只用于独立子文档，不得反向套到父级汇总页。

模板名称、执行步骤、验收规则只存在于本文件，不能复制进子文档正文。正文不得出现“按 GPT-5.5 模板”“规范化摘要”“优先保留”“后续继续补”等面向 Agent 的提示语。

### 读者正文隔离

正文不能出现图片选择、章节落点或写作过程的说明。以下句式属于内部执行备注，禁止上传：

- “下面使用完整发布页逻辑区块”
- “把具体榜单放到 Benchmark 逐项拆解”
- “避免用一张总览图代替能力分析”
- “不再使用截断截图”
- “应写成…… / 不能写成……”
- “普通截图不纳入 Demo 证据”

同一意思应改写为读者可直接理解的事实判断，例如“速度是该模型最明确的优势”“该成绩处于中上位置”“发布材料显示其产品定位是……”。写入前后都要扫描正文 block；validator 的 `reader_text_hits` 不是空数组时，不能标记子文档完成。

内部工作说明也不得改写成看似正式的正文。例如“社区反馈按支持、质疑和可用性争议分开记录”“每列保留一张图”“后续补充来源”仍然是在指导 Agent，不是面向读者的内容，必须留在 manifest 或校验报告中。正文应直接写具体的支持观点、质疑点、证据强弱和当前缺口。

## 页面骨架

下面的顺序来自参考页的真实 block 结构。章节内容按模型实际发布调整，但不能把它压缩成一段“规范化摘要”。

### 0. 读者摘要 Callout

第一个根级 block 使用 callout，直接写给读者：

- 1–2 句核心判断：这次发布准备是否充分、真正主打什么、最明显的领先项和短板。
- 1 句定位：coding、知识工作、科研、多模态、安全或成本中，哪些是主线。
- 2–4 条可点击官方来源：产品页、技术报告、System Card、开发者文档。

禁止写“按模板整理”“规范化摘要”“社区反馈应该怎么分类”等内部说明。

### 1. 四列开场证据

callout 后紧接一行四列图片，快速展示最值得看的四份证据。参考页放的是四张 benchmark / 能力结果缩略图，而不是四张宣传海报。

- 四张图必须覆盖至少 3 类来源：`官方网页 / 文档`、`官方社媒`、`GitHub / 模型仓库 / 生态接入`、`独立 benchmark / Arena / 模型市场`、`外部媒体 / KOL`。不能四张都来自官网，也不能把一张官方 benchmark 拆成四格。
- 同一张原始 benchmark 最多占一格。左右裁图、上下裁图、局部放大和完整表格仍算同一个原始来源；四格内禁止同时出现。
- GitHub 图必须直接出现模型名，并证明发布、接入、兼容、配置或真实使用。找不到相关仓库证据时，改用独立评测、模型市场、外部媒体或官方社媒，不能为了凑渠道放无关代码页。
- 每个候选图必须先用 `view_image` 打开验收。404、注册弹窗、登录墙、骨架屏、半截表头、裁断图例、不可读小字和无关页面全部淘汰；不会裁时直接保留完整网页或完整逻辑区块。
- manifest 必须为四格逐项记录 `source_class`、`source_url`、`source_original`、`visual_check` 和最终落点；缺任一项不得标记完成。
- 开场图只做视觉索引；后文用文字解释对应结论，不再次插入同一文件。
- 不强制逐列图注，但图片内容必须能在后文明确找到对应小节。

### 2. 基本信息

用 5–8 条 bullet 完成硬参数和集中判断：发布时间与时区、定价、上下文、输出长度、模态、可用渠道、训练或架构变化，以及一条包含领先项和短板的核心结论。关键数字可以用飞书高亮，但不要整段荧光色。

基本信息后使用一行两列证据，例如官方对比表与独立评测 / Arena 总览。若 Artificial Analysis evidence policy 为 `available`，至少分别截图模型总览和 benchmark / 排名分解两类证据，图片下面写清对应指标和区块；若为 `checked_unavailable` 或 `not_applicable`，使用 manifest 中记录的替代证据，不放占位图。

### 2A. 商业与定价（启用 business-v1 时）

这一章面向市场、销售和产品读者，写入现有模型子 Wiki，不新建同名模型页。使用 `scripts/render_pricing_report.py` 生成的本地 Markdown 作为唯一正文底稿，保留每百万 token 的输入、输出、缓存和批处理分列，以及官方 / OpenRouter 的供应商、端点、路由、区域、档位和生效日期。不同币种或上下文档位不得合并；未公开写“未公开/不可用”，不得填零。

定价后可以放榜单能力簇和业务标签，但必须区分模型分数、排名、榜单版本与方法变化。AA 的任务替换、类别权重、单项权重和模型结果分开写；没有方法原文就写未知，不从截图推出因果。Coding / Agent（包括 DeepSWE、Terminal-Bench、CyberGym 等待核对项目）单独归类并记录工具、数据集、harness、采样和可比性。

### 3. 模型特点 + 展示 Case

这部分不是固定两张图，而是按模型真实能力拆成多个 Heading 2 小节。参考页依次写了 Agentic Coding、知识工作 / 企业工作流、科学研究、网络安全、System Card、Token 效率与价格。

每个能力小节可以组合：

- 1 段事实判断或引用型 callout。
- 1–3 条指标、合作方反馈或任务说明。
- 一行两列 Case 图，图下写“任务 + Prompt / 工具 / 过程 + 结果”。
- 需要强调单一结果时，可以放有文字承接的根级单图。

优先写当前模型真正有材料的能力，不要求每篇都复制参考页的所有小节。没有科研或安全材料就不建空章节。Case 没有数值时写交付物、运行时长、迭代轮数和人工介入程度，不能只写“效果很好”。

### 4. 安全 / System Card / Token 效率（条件章节）

只有官方明确强调时加入，并放在 Benchmark 之前：

- 安全能力可以使用“图表 + 分析 bullet”的两列布局。
- System Card 可以用三列表格比较“维度 / 本厂商 / 主要对手”，图片不得进入表格。
- Token 效率与价格可以使用“效率图 + 单任务成本与定价解释”的两列布局。

### 5. Benchmark

先用一段话给整体判断，再放两列 grid：

- 左列按 Coding、Agent、computer use、知识工作、推理、视觉等类别列关键分数、领先项和落后项。
- 右列放一张完整 benchmark / Arena 对比图，保留表头、第一行、最后一行、图例和脚注。

grid 后补一条模型特定的关键判断，不能写“分项看领先项、短板和成本”这种给 Agent 的通用提醒。

### 6. 发布过程

#### 发布目标和策略

写清发布时间选择、代号 / teaser、产品 rollout、API 是否同步、企业或开发者目标，以及相对上一代最大的变化。

必须有一张发布对比表，默认三列：

| 维度 | 上一代 / 主要竞品 | 本次发布 |
|---|---|---|
| 发布间隔 |  |  |
| 预热手法 |  |  |
| 核心叙事 |  |  |
| 合作伙伴 / 外部背书 |  |  |
| API 与产品节奏 |  |  |
| 定价方向 |  |  |

维度可以按实际资料调整，但至少保留 4 行有效对比。

#### 发布过程与社区声势

分开写四类证据，不能混成一段：

1. 官方官宣：官方 X / 微信 / 博客的首发帖和核心口号
2. 合作伙伴：云厂商、客户、投资方或企业共同官宣
3. 客户评价：官网引用了多少家公司，挑 2–4 条最有代表性的原意概括
4. 社区反馈：高赞支持、主要质疑、价格 / benchmark / 可用性争议

先用两列承载官方发布过程：一列放官宣中的具体 Case / 视频与文字说明，另一列放完整官方社媒帖。随后用三列区分“合作伙伴 / 共同官宣”“官网客户评价”“社区反馈”。

三列是语义分栏，不是图片配额：参考页中有的列放多张合作伙伴帖，有的列只有客户原话或社区评论。没有直接证据时保持纯文字，不得为了每列有图塞普通转发、无关 benchmark 或重复 Case。完整社媒帖必须保留作者、正文、媒体、时间和互动区。

### 7. 社区 Demo

收录 2–4 个有代表性的外部复现。每个 Demo 写：

- 来源 URL 和作者
- 使用的模型 / 工具 / Prompt
- 生成了什么
- 是否一次成型、耗时多久、有什么限制

每行两列，一列文字、一列截图；多个 Demo 分成多行，不做四图拼接。

### 8. MiniMax 可以借鉴的

用 3–5 条可执行建议收尾。每条都要回扣前文证据，例如：

- 用可复现 Prompt 降低 Demo 的“剪辑感”
- 用代号 / teaser 低成本撬动 UGC
- 让合作伙伴 Day 0 同步官宣
- 用 token 效率或单任务成本解释价格变化

不要写空泛的“加强宣发”“提升影响力”。

### 9. 官方资源与返回链接

文末保留：

- 官方发布页
- 开发者文档 / API 文档
- System Card / 技术报告（如有）
- 官方社媒首发帖
- `返回汇总页` 可点击链接（`text_run` link 或 `mention_doc`，不能只粘贴普通 URL）

## 排版合同

- 标题格式：`【YYYY/MM/DD】<模型>：<一句话主题>`。
- 视觉验收只与本文件对应的 GPT-5.5 参考页和四张确认截图比较；不得因为其他子文档也有同类错误就判定合格。
- 主章节使用 Heading 1，小节使用 Heading 2；Heading 3 只在真实三级内容存在时使用，不能直接挂在文档根级。
- 标题审计必须基于 `parent_id` 和根级 `children`：`block_type: 3/4/5` 分别是 H1/H2/H3，扁平 block 列表中的 grid 后代不能被误判为根级标题。
- grid 内的产品定位、生态承接、Case 名、benchmark 名、`Benchmark：质量与 token 效率`、AA 榜单名和图注使用加粗普通正文，不创建 Heading block。标题级别只服务于根级章节和真正的小节，不要为了视觉强调滥用 H2/H3。
- 开场证据墙使用四列；能力 Case 通常两列；发布过程 / 合作伙伴 / 客户评价 / 社区反馈允许三列。不要把这三种布局统一压成两列。
- 除开场四列证据墙外，每张图必须在同列或紧邻根级位置有对应文字；短图注优先，但允许像参考页一样用 1–2 句 Case 说明承担图注作用。
- 子文档保留高分辨率原图，不设置父页的 `600x300`、`720x480` 或 `720x1000` 上限，不在上传前重采样；飞书负责按页面宽度展示，读者仍可点开原图查看细节。
- 允许有文字承接的根级单图；仍然禁止表格内图片、无上下文的孤立图片和纯宣传海报。官网整页长截图不是默认选择，但当局部裁图无法完整保留表头、首尾行、坐标轴、图例、作者、正文、时间或互动区时，必须使用完整网页 / 完整文章 / 完整当前帖子，不能交付半截截图。
- 图片不得出现上一行 / 下一行残片、半截标签、被裁掉的图例或右侧侧栏窄条。无法干净去除这些内容时，保留完整页面优先于继续裁剪。
- Artificial Analysis 按 manifest 的证据策略执行。状态为 `available` 时至少需要两张互不重复、实际放入子文档的 AA 图：一张覆盖 Intelligence / 速度 / 价格 / 上下文等模型总览，一张覆盖 Intelligence、Agent、coding、cost 或其他可见 benchmark / 排名分解；每张图必须对应不同 `source_section`、`content_sha256`、`child_image_block` 和独立 manifest 记录。状态为 `checked_unavailable` 或 `not_applicable` 时，不强制 AA 图片，但必须记录检查 URL、原因和替代证据。
- 能力 / Case 图片必须是官方图表、真实任务结果、产品输出或可核对的外部评测；禁止使用程序生成的“核心能力 / 展示 Case”摘要卡或占位卡。
- 三列发布 / 社区区块不规定每列图片数量；图片数量由真实证据决定。某列纯文字是合法状态，同一张 benchmark、社媒帖或 Demo 不得在多个章节反复出现。
- 开场四列中的图片只做视觉索引，后文用文字展开对应结论，不再次插入同一图片。图片必须能从可见内容直接支持邻近文案，不能用无关网页、普通转发、截断表格或内部生成摘要卡占位。
- 子文档默认 2500–6000 个中文字符；资料很少时可以短，但不能删掉 Benchmark、发布过程和可借鉴点。
- 主观判断集中在“基本信息”“发布目标和策略”“MiniMax 可以借鉴的”；其他章节以事实和证据为主。

## 完成前检查

运行：

```bash
python3 scripts/validate_child_document.py --helper <feishu_helper.py> --doc <child_doc_or_wiki_token> --parent-node <actual_parent_node_token> --manifest <研究文件夹>/update-manifest.json
```

`--helper`、`--parent-node` 和 v3 `--manifest` 都是必填参数。`--helper` 必须指向当前运行时已确认存在的兼容飞书 helper；`--parent-node` 必须使用当前目标的 API 回读值。校验器不会再默认读取私人目录中的 helper，也不会默认指向某个固定 Wiki 节点。

子页 validator 通过后还需统一 sync_run.py verify 保存结果、复核当前远端并运行最终门禁，才能标记本次交付完成。
